# Audit visual dan fungsi POS — 2 November 2026

## 1. Tujuan, baseline, dan batas audit

Dokumen ini adalah backlog implementasi dan panduan serah-terima untuk agent berikutnya. **Audit ini tidak memperbaiki source aplikasi, tidak melakukan push, dan tidak melakukan deploy.** Script audit dan bukti memakai data sintetis.

- Repository: `prima-motor-pos`, branch `main`, commit yang diaudit: `7f93010`.
- Halaman utama: `Frontend/src/pages/pos.tsx` (4.950 baris pada baseline).
- Cakupan: katalog/pencarian, keranjang multi-item, tier harga, pelanggan, mekanik, pembayaran, catatan/lampiran, konfirmasi, detail/deep link, edit/hapus, pelunasan cepat, cetak, draft, akses, dan gaji yang berada di POS.
- Pemeriksaan visual langsung: browser Chromium lokal, viewport 1280×900 dan 390×844, form Service, tab pembayaran/catatan, detail, dan edit lampiran. Navigasi level 10 diuji dengan akun tiruan.
- Pemeriksaan fungsi: penelusuran source, suite tes frontend, helper murni, serta browser dengan seluruh endpoint API diintersep. Mutasi bisnis diblokir.
- **Belum diuji ulang dalam audit ini:** CRUD terhadap PocketBase terisolasi, konflik dua kasir di server, backend produksi, printer fisik/RawBT, upload file nyata, Cloudflare, Safari/iOS, 320px/tablet, dan seluruh jenis transaksi end-to-end.
- Tidak membaca isi transaksi operasional. Status server produksi dan tampilan hasil build yang sedang dilayani tidak disimpulkan dari hasil localhost.

### Arti status bukti

- **B — Browser:** perilaku diamati pada fixture browser; bukan bukti mutasi server.
- **H — Helper:** direproduksi dengan menjalankan fungsi murni.
- **K — Kode:** jalur source mendukung temuan; skenario interaktif/server belum direproduksi.
- **R — Risiko:** perlu reproduksi tambahan sebelum dianggap bug operasional terkonfirmasi.
- **U — Usulan UX:** perbaikan pengalaman penggunaan, bukan klaim kegagalan transaksi.

P1 = risiko data/uang/akses yang perlu didahulukan. P2 = masalah alur, ketepatan tampilan, atau aksesibilitas. P3 = pemeliharaan dan penyempurnaan. Tidak ada P0 yang dibuktikan dalam audit ini.

## 3. Temuan dan instruksi implementasi

### POS-01 — Draft edit berubah menjadi create setelah reload

**P1 · B/K.** Sumber: `pos.tsx:151`, `pos.tsx:502`, `pos.tsx:1644`, `pos.tsx:2097`; `lib/posDraft.ts`.

Browser: buka detail fixture → Edit → konfirmasi → modal **Edit Service**. Draft tersimpan hanya mempunyai `cart`, `selectedMenu`, `formBayar`, `savedAt`. Reload → modal menjadi **Transaksi Service** dan banner identitas edit hilang. Handler simpan membedakan create/edit berdasarkan `editSession`, yang tidak ikut dipulihkan. Tidak dilakukan simpan ke server untuk membuktikan duplikasi aktual.

**Dampak:** pengguna dapat mengira sedang melanjutkan revisi, padahal berikutnya diarahkan ke pembuatan transaksi baru.

**Eksekusi:**

1. Buat draft versioned dengan discriminated union `mode: create | edit`.
2. Simpan `menuId`, konteks transaksi, dan snapshot awal yang diperlukan untuk konflik. Jangan memulihkan edit dari isi keranjang saja.
3. Saat restore edit, muat ulang record dan child terkait; bandingkan snapshot. Jangan mengganti snapshot awal diam-diam sehingga konflik dianggap valid.
4. Bila record sudah dihapus/tidak dapat dibaca, blokir submit edit dan sediakan pilihan eksplisit membuat salinan baru atau membuang draft.
5. Pertahankan receipt pending sebelum mengizinkan restore/submit.

**Selesai jika:** reload edit tetap menunjukkan ID/mode edit; submit memakai update ID sama; receipt pending, record terhapus, dan record berubah mempunyai pengujian; jumlah menu tidak bertambah akibat melanjutkan edit.

### POS-02 — Lampiran lama terduplikasi sebagai file baru

**P1 · B/K.** Sumber: `pos.tsx:2203`, `pos.tsx:1773`, `pos.tsx:3485`.

`handleEditHistoryToCart` mengunduh file lama menjadi `File`, lalu menaruh daftar yang sama ke `menuFiles` dan `existingMenuFiles`. Browser menunjukkan `evidence.png` dua kali: **Tersimpan** dan **Belum disimpan**, serta menghitung satu file baru tanpa pengguna memilih upload. Saat edit, `menuFiles` dikirim dengan `file+`.

**Dampak:** duplikasi upload, jumlah lampiran salah, ukuran batch membesar; tombol hapus file baru membingungkan karena salinan tersimpan tetap ada. Persistensi duplikasi server belum diuji.

**Eksekusi:** pisahkan `existingAttachments: {name,url}[]`, `newFiles: File[]`, dan daftar penghapusan eksplisit bila fitur hapus file lama memang diinginkan. Jangan unduh ulang file lama untuk keperluan menyimpannya. Hanya kirim `file+` untuk upload baru; `file-` hanya untuk pilihan penghapusan pengguna sesuai kontrak PocketBase. Periksa `response.ok` saat mengambil preview dan kelola object URL dengan cleanup.

**Selesai jika:** edit tanpa mengubah media menghasilkan nol operasi file; tambah satu file menghasilkan tepat satu file tambahan; file lama tetap tampil sekali; request preview gagal tidak menjadi file HTML error yang terunggah.

### POS-03 — Draft global lintas pengguna

**P1 · K.** Sumber: `lib/posDraft.ts:3`, pemanggilan localStorage di POS, serta `lib/session.ts`.

Key `pos_draft_cart` tidak menyimpan owner ID; restore tidak mencocokkan akun. Sesi sengaja mempertahankan draft ketika logout/expired. Pada browser yang dipakai beberapa kasir, draft akun A berpotensi dipulihkan saat akun B login.

**Eksekusi:** gunakan key beridentitas pengguna dan pemeriksaan owner dalam payload, selaraskan dengan receipt `prima_atomic_pending:<user>`. Migrasi draft legacy harus konservatif: jangan otomatis menganggap draft tanpa owner milik pengguna berikutnya. Berikan pilihan pemulihan yang jelas tanpa membuka data akun lain.

**Selesai jika:** A→logout→B tidak menampilkan draft A; A login kembali dapat memulihkannya; pending receipt A tidak dibersihkan atas nama B; expiry/migrasi/corrupt JSON teruji.

### POS-04 — Klasifikasi jenis transaksi menggunakan default berbahaya

**P1 · H/K, verifikasi makna bisnis sebelum memperbaiki.** Sumber: `lib/posTransactions.ts:1`, `pos.tsx:1807`, `pos.tsx:1922`, `pos.tsx:2320`.

Helper mengembalikan `false` untuk `Grosir`. Jalur create menganggap selain Penjualan/Service/Servis sebagai stok **in** dan kas **out**. Theme POS mengenal Grosir. Jika dropdown operasional memakai nama `Grosir` untuk penjualan grosir, arah stok/kas akan terbalik. Audit tidak membaca dropdown produksi sehingga keberadaan pilihan tersebut di produksi belum dikonfirmasi. Retur juga memerlukan asal transaksi, bukan default tunggal.

**Eksekusi:** buat satu registry jenis transaksi dengan arah stok, kas, dukungan mekanik, harga dasar, dan validasi. Petakan alias service/servis. Jenis tidak dikenal harus ditolak secara informatif. Tentukan retur penjualan vs retur pembelian dari hubungan asal atau pilihan eksplisit; jangan menebak. Gunakan registry yang sama pada create, edit, quick settle, detail, dan struk.

**Selesai jika:** tabel pengujian tiap jenis membuktikan create→edit→delete mengembalikan nilai awal; Grosir penjualan mengurangi stok/menambah kas; jenis tidak dikenal tidak masuk default mutasi.

### POS-05 — Pelanggan draft ditimpa setelah fetch

**P1 · K.** Sumber: effect `fetchFilteredPersons`, `pos.tsx:1067–1100`; effect reset online `pos.tsx:1311`.

Form diinisialisasi dari draft, tetapi setelah dropdown customer/supplier selesai dimuat, effect menetapkan default Umum1 atau supplier pertama ketika bukan edit. Pelanggan khusus/online yang telah dipulihkan tidak dipertahankan. Perubahan ini dapat mengubah tier harga dan mereset marketplace/admin/cashback.

**Eksekusi:** pertahankan pilihan draft jika masih valid dan boleh diakses; default hanya untuk form baru kosong. Jika pelanggan sudah tidak tersedia, tampilkan error dan minta pilihan baru, jangan mengganti diam-diam. Bedakan status “opsi belum selesai dimuat” dari “pelanggan offline” agar effect tidak menghapus field online lebih awal.

**Selesai jika:** restore pelanggan khusus/online, termasuk fetch lambat, menjaga pelanggan, tier, dan biaya; pelanggan terhapus memunculkan keputusan eksplisit.

### POS-06 — Konflik edit gaji belum setara edit transaksi biasa

**P1 · K/R.** Sumber: `pos.tsx:729`, `pos.tsx:896`; `Backend/pb_hooks/lib/atomic_ledger.js:154`.

Edit POS biasa mengirim `atomic_expected`; `gajiEditSession` hanya memuat menu ID dan update gaji tidak menyertakan snapshot serupa. Atomicity mencegah setengah transaksi, tetapi tidak otomatis mencegah overwrite revisi kasir lain. Perlu uji konkurensi terisolasi untuk memastikan pengaman backend lainnya.

**Eksekusi:** simpan snapshot periode dan child salary yang relevan. Gunakan kontrak expected yang didukung backend; tambahkan dukungan konflik child jika pemeriksaan parent tidak cukup. Jangan mengubah migrasi lama; jika perlu perubahan skema gunakan migrasi tambahan. Tampilkan konflik sebagai “data berubah, muat ulang”, tanpa retry buta.

**Selesai jika:** dua editor membuka periode sama; editor B tidak menimpa perubahan A; saldo bon dan gaji tetap konsisten ketika terjadi konflik.

### POS-07 — Autofill gaji dapat menerapkan respons karyawan sebelumnya

**P1 · K/R.** Sumber: `pos.tsx:331–399`.

`handleSelectPerson` memanggil getFullList dengan auto-cancel false, tanpa generation guard. Respons A yang datang setelah pemilihan B dapat mengatur `person` dan komponen kembali ke A. Input juga dapat ditimpa autofill ketika pengguna mulai mengetik selama request berjalan.

**Eksekusi:** gunakan generation/request ID, abaikan respons yang tidak lagi sesuai person/session. Batalkan/invalidate saat modal ditutup atau slip lain dibuka. Tentukan apakah field dikunci selama loading atau autofill hanya mengisi field belum disentuh. Reset status “diisi dari slip lama” saat person berubah.

**Selesai jika:** respons A dibuat lebih lambat dari B; form tetap B; input manual tidak tertimpa respons terlambat; respons setelah close/reopen tidak mengubah slip baru.

### POS-08 — Level 10 tidak mendapat navigasi input

**P2 · B/K.** Sumber: `components/pos/PosNavbar.tsx`, filter `userLevel !== '10' || ...overview`.

Akun fixture level 10 hanya melihat Overview, tidak melihat Service/Penjualan/dll. Ini bertentangan dengan kebijakan DATASOURCE: semua akun aktif dapat tambah/ubah operasional.

**Eksekusi:** pisahkan izin create/update dari izin baca privat/delete/admin. Tampilkan menu operasional yang sesuai kebijakan untuk akun aktif. Pertahankan filter gaji pribadi dan izin backend; jangan menghapus semua pengecekan level secara massal.

**Selesai jika:** matriks level 1, 2, 5, 10 membuktikan create/update tersedia sesuai kebijakan, sementara delete tetap sesuai endpoint permission dan gaji tetap privat.

### POS-09 — Draft tidak mencakup semua pekerjaan POS

**P2 · H/K.** Sumber: `lib/posDraft.ts`, `pos.tsx:502`, `pos.tsx:4284`, `pos.tsx:4467`.

Service sah tanpa barang dapat memiliki mekanik/ongkos/catatan, tetapi cache hanya disimpan/dipulihkan jika cart berisi item. Draft gaji tidak masuk mekanisme cache; close periode membersihkan list/header. Lampiran File juga tidak dapat dipulihkan hanya dengan serialisasi JSON biasa.

**Eksekusi:** definisikan dirty draft berdasarkan seluruh form, bukan panjang cart. Integrasikan draft gaji/periode dan edit context. Putuskan penyimpanan attachment via IndexedDB atau berikan indikator “pilih ulang lampiran”; jangan menjanjikan file tersimpan jika hanya nama yang tersimpan. Bedakan Tutup, Batal edit, dan Buang draft.

**Selesai jika:** Service tanpa produk dan draft gaji bertahan setelah navigasi; membuang draft memerlukan aksi jelas; expiry, owner, dan pending atomic tetap benar.

### POS-10 — Validasi numerik belum menyeluruh

**P2 · H/K.** Sumber: `lib/posValidation.ts`, `pos.tsx:1410`, `pos.tsx:3276`, form gaji.

Probe `validateCheckout` mengembalikan array error kosong untuk nominal pembayaran negatif dan NaN. Validator hanya memeriksa nominal sama dengan nol/akun kosong. Harga manual juga diisi langsung; gaji tidak mempunyai validasi domain terpusat sebelum review. Ini **bukan bukti backend menerima angka tersebut**; UI dapat tetap menghitung/review nilai tidak valid sebelum backend menolaknya.

**Eksekusi:** normalisasi angka dan validasi `Number.isFinite`, batas minimum/maksimum, jumlah bulat jika unit menuntutnya, nominal >0 untuk baris aktif, serta aturan nol untuk field opsional. Cek tiap mekanik terpilih, bukan hanya keberadaan satu mekanik valid. Validasi juga pada handler submit, bukan mengandalkan atribut HTML. Untuk netto gaji negatif/diterima berbeda jangan menetapkan kebijakan baru tanpa keputusan bisnis.

**Selesai jika:** negatif, NaN, Infinity, kosong, duplikasi baris, dan nominal sangat besar mempunyai error field yang tepat; tidak ada request batch untuk payload invalid.

### POS-11 — Nominal pada struk tidak selalu mengikuti pembayaran

**P2 · K.** Sumber: input pembayaran `pos.tsx:3276`, shortcut F9 `pos.tsx:1479`, receipt `pos.tsx:2015`.

Input manual memperbarui `cashflowList`, sedangkan receipt baru mengambil cash/change dari `formBayar.nominalBayar`. Field nominalBayar hanya disetel pada alur tertentu seperti auto-lunas. Pengguna yang mengetik pembayaran manual bisa mendapatkan nilai struk berbeda dari total pembayaran.

**Eksekusi:** definisikan perbedaan uang diserahkan pelanggan, kas benar-benar dibukukan, pembayaran gabungan, dan kembalian. Ambil semua tampilan dari model terpusat; jangan sekadar menyamakan dua field bila artinya berbeda. Setelah commit gunakan hasil transaksi terkonfirmasi untuk struk.

**Selesai jika:** manual/auto-lunas/multi-akun/pembayaran sebagian/kelebihan menghasilkan struk dan jurnal yang sesuai; cetak ulang konsisten dengan cetak pertama.

### POS-12 — Relasi legacy tidak dibaca seragam

**P2 · K.** Sumber: `loadHistorySubDetails` sekitar `pos.tsx:989`; `handleEditHistoryToCart` sekitar `pos.tsx:2110–2180`; save `pos.tsx:1674`.

Save/edit stock mencari `ref OR ref_baru`, tetapi detail stock/cashflow/ongkos serta pemuatan cashflow/ongkos saat edit memakai hanya `ref_baru`. Record lama yang masih memakai `ref` dapat tampil kosong atau tidak dimuat ke form. Simpan berikutnya membaca himpunan berbeda dari yang pengguna lihat.

**Eksekusi:** gunakan helper relasi yang sama untuk load/detail/edit/delete; bila seluruh legacy sudah dimigrasikan, verifikasi dengan audit read-only sebelum menghapus fallback. Hindari fallback berbasis ID tanpa mengetahui koleksinya.

**Selesai jika:** fixture relasi lama, baru, dan campuran mempunyai jumlah item/pembayaran/mekanik sama pada detail, edit, dan struk; edit tidak menghapus child yang tidak sempat ditampilkan.

### POS-13 — Respons lama dapat menimpa state baru; kegagalan fetch diam

**P2 · K/R.** Sumber: `fetchData` sekitar `pos.tsx:1103`, `loadHistorySubDetails` sekitar `pos.tsx:989`, `handleEditGajiFromHistory:896`.

Beberapa request memakai auto-cancel false dan menulis state tanpa memeriksa ID/generation. Buka detail A lalu B pada jaringan lambat dapat berisiko menampilkan child A pada header B. Error fetch hanya dicatat ke console sehingga pengguna dapat melihat daftar kosong tanpa membedakan “tidak ada” dan “gagal”. Edit gaji juga memakai `historyGajiSubItems` bila non-kosong tanpa memastikan kepemilikan parent.

**Eksekusi:** simpan loading/error/request ID per list/detail; verifikasi parent ID sebelum menerapkan hasil atau membuka editor. Reset halaman ketika filter membuat pagination tidak valid. Tambahkan Retry read-only dan status stale yang jelas; jangan memakai data lama sebagai data sukses baru.

**Selesai jika:** respons dibalik urutannya tidak menukar isi; HTTP 403/500/offline menampilkan state berbeda dari empty; editor tidak terbuka dengan children milik transaksi lain.

### POS-14 — Quick settle menolak berdasarkan saldo cache

**P2 · K/R.** Sumber: `pos.tsx:2323–2328`.

Sisa tagihan diambil ulang, tetapi `saldoAwal` berasal dari `cashflowAccounts` lokal dan `saldoAkhir < 0` langsung melempar error. Saldo yang sudah bertambah oleh transaksi lain bisa membuat pembayaran valid ditolak sebelum ledger memeriksanya.

**Eksekusi:** gunakan data akun terbaru untuk preflight atau perlakukan nilai cache sebagai estimasi saja. Backend tetap otoritas saldo dan snapshot konflik. Setelah berhasil, muat ulang juga jurnal pembayaran detail yang sedang terbuka, bukan hanya header nota/akun.

**Selesai jika:** saldo di server berubah setelah modal dibuka; kasir tidak memperoleh penolakan palsu dari cache; saldo tidak cukup tetap ditolak server; tab pembayaran langsung menampilkan baris pelunasan baru.

### POS-15 — “Belum lunas” dapat berarti bukti belum lengkap

**P2 · K/U.** Sumber: `pos.tsx:1728–1735`, tombol pelunasan `pos.tsx:4112`.

Pembelian baru tanpa media dipaksa status `belum` meskipun total pembayaran cukup. Detail kemudian dapat menampilkan status belum lunas dengan sisa nol. Aturan bukti ini sudah ada dan tidak boleh dihapus tanpa keputusan bisnis.

**Eksekusi:** pisahkan status pembayaran dari status bukti, atau setidaknya tampilkan alasan “Pembayaran penuh, bukti belum lengkap”. Aksi berikutnya harus “Lengkapi bukti”, bukan meminta pembayaran lagi. Periksa konsistensi create/edit/quick settle dan migrasi record historis sebelum perubahan schema.

**Selesai jika:** pembelian lunas tanpa bukti tidak mendorong pembayaran ganda; pengguna dapat memperbaiki bukti; aturan bisnis asli tetap dipenuhi.

### POS-16 — Field tidak memiliki label programatik

**P2 · B/K.** Browser menemukan 7 input/select/textarea tanpa `aria-label`, `aria-labelledby`, atau asosiasi `<label>` pada fixture form. Termasuk waktu, pelanggan, ongkos, akun kas, nominal, dan catatan. Teks judul visual saja tidak selalu menjadi nama aksesibel.

**Eksekusi:** tambahkan ID stabil dan `htmlFor`, label spesifik per baris (misalnya “Nominal pembayaran 2”), `aria-describedby` untuk bantuan/error, dan `aria-invalid`. Jangan gunakan placeholder sebagai satu-satunya label. Tetap pertahankan nama aksesibel qty/harga produk yang sudah tersedia.

**Selesai jika:** semua field editable dapat ditemukan lewat `getByLabel`; reader mengumumkan fungsi dan error; fokus berpindah ke field pertama yang invalid termasuk ketika berada pada tab lain.

### POS-17 — Escape dan modal bertumpuk tidak konsisten

**P2 · B/K/R.** Sumber: shortcut `pos.tsx:1444`, shared `components/modal.tsx`.

Browser: buka keranjang biasa → tab Catatan → tekan Escape, modal tetap terbuka (`escapeClosedCart=false`). Handler Escape bergantung pada `isPaymentFormOpen`, sedangkan tombol buka keranjang/berpindah tab memakai state lain. Shared Modal belum menangani Escape dan setiap modal memiliki focus trap sendiri; confirm overlay di atas detail dapat berisiko membuat dua trap aktif.

**Eksekusi:** tetapkan satu pemilik modal aktif atau modal stack. Escape menutup hanya dialog paling atas bila tidak processing; aksi berisiko kehilangan draft harus mengikuti aturan dirty state. Background modal inert; saat ditutup fokus kembali ke pemicu yang masih mounted.

**Selesai jika:** Escape konsisten pada form/detail/review/gaji/confirm; Tab tidak keluar dialog teratas; tidak ada modal belakang menangkap shortcut; tidak bisa menutup proses commit dengan cara yang menimbulkan retry ganda.

### POS-18 — Success alert disajikan sebagai peringatan

**P2 · K.** Sumber: `pos.tsx:4220–4250`.

Renderer lokal memakai `isAlert ? 'rose' : 'blue'` dan ikon AlertTriangle untuk seluruh `dialog.type === 'alert'`, termasuk pesan sukses. Class warna dirakit dinamis; keberadaannya dalam CSS hasil build perlu diverifikasi, bukan diasumsikan tersedia oleh Tailwind.

**Eksekusi:** gunakan status eksplisit `success/error/warning/info/confirm` dan map class statis/shared Modal alert. Untuk error uncertain commit, hindari label yang mendorong create ulang sebelum receipt resolved. Bedakan error penyimpanan dari error refresh sesudah commit.

**Selesai jika:** sukses berikon/tone sukses; validasi, network error, permission denied, pending receipt dan conflict memiliki pesan/action yang berbeda; seluruh class muncul di build terisolasi.

### POS-19 — Hasil pencarian relasi dapat terpotong

**P2 · K.** Sumber: `pos.tsx:1115–1134`.

Lookup `log_stock` dan `ongkos` hanya mengambil halaman 1 berisi 100 record untuk mencari parent menu. Jika lebih banyak hasil cocok, nota lain tidak ikut dicari, tanpa indikator bahwa pencarian parsial.

**Eksekusi:** utamakan pencarian parent berbasis relasi di server atau endpoint paginated khusus; bila memakai iterasi client, tetapkan limit dan tampilkan status parsial. Jangan mengubah menjadi getFullList tanpa menilai ukuran data/performa.

**Selesai jika:** fixture >100 child yang cocok tetap menghasilkan parent yang relevan pada pagination hasil; error salah satu lookup tidak disamarkan sebagai hasil lengkap.

### POS-20 — Penyederhanaan visual berikutnya

**P3 · B/U.** Bukti: screenshot form desktop/mobile, pembayaran, dan detail di folder bukti.

Yang sudah baik: modal dibatasi lebar, backdrop terlihat, footer total/aksi menetap, tab jelas, ikon+teks pada aksi utama, dan pada 390px tidak ada overflow horizontal. Detail memisahkan ringkasan, barang/jasa, dan pembayaran.

Yang bisa ditingkatkan:

1. **Kepadatan form mobile:** tanggal dan pelanggan memakai card bertingkat sehingga kontrol qty/harga item pertama belum terlihat pada viewport awal. Padatkan blok metadata dengan label+field yang lebih sederhana; tampilkan identitas dan kontrol item sebelum informasi tier lanjutan. Jangan menyembunyikan field wajib.
2. **Nominal pembayaran:** field menampilkan `85000`, sedangkan total `Rp 85.000`. Pertimbangkan input angka berformat lokal saat blur dengan caret dan copy/paste yang benar; format tidak boleh mengubah nilai yang disimpan.
3. **Hierarki dan keterbacaan:** banyak teks helper berukuran 10–11px. Uji target 12–14px untuk informasi penting, zoom 200%, landscape, keyboard layar, dan safe area. Kontras belum diukur; jangan mengklaim patuh WCAG berdasarkan screenshot saja.
4. **Detail gaji banyak karyawan:** komponen detail individual lengkap untuk setiap karyawan dapat membuat scroll panjang. Pertimbangkan daftar ringkas → drilldown slip tanpa kehilangan ringkasan periode, aksi edit/cetak, maupun lampiran.
5. **Kode/label produk:** formatter menggabungkan field mentah. Fixture awal dengan properti opsional hilang memperlihatkan kata `undefined`; perbaiki dengan daftar field nonkosong. Screenshot final memakai fixture lengkap; tidak ada klaim bahwa data produk produksi rusak.

**Selesai jika:** pada 390px field utama/total/action mudah ditemukan; pada 320px dan keyboard terbuka tidak ada field/button terpotong; label panjang dan nominal besar tidak menutupi aksi; harga tier, override, dan error tetap terbaca.

### POS-21 — Pemisahan domain logic dari presentasi

**P3 · K.** POS mengelola transaksi, gaji, fetch, receipt, modal, dan draft dalam satu komponen besar. Pemisahan ini harus dilakukan bertahap setelah tes perilaku tersedia.

**Eksekusi:** ekstrak tipe/domain murni terlebih dahulu: transaction kind policy, money model, draft schema, attachment diff, dan salary validation. Baru pisahkan hooks data/draft dan modal. Jangan melakukan rewrite CRUD besar bersamaan dengan perubahan desain; risiko ledger/revert harus tetap dapat ditinjau per commit.

**Selesai jika:** perubahan komponen tidak mengubah payload dan expected snapshot; golden tests untuk payload, nilai revert, tier, dan receipt tetap lulus.

## 4. Hal yang wajib dipertahankan

- `createFinancialBatch` memakai ID record stabil per batch, receipt idempotensi, marker commit, dan resolve saat respons tidak pasti. Jangan mengganti dengan request berurutan untuk stok/saldo.
- Edit dan delete harus membalik efek lama lalu menerapkan nilai baru dalam satu transaksi database.
- `submitLockRef` mencegah submit ganda; watchdog hanya memberi status, bukan melepas lock.
- Quick settle membaca ulang menu dan memakai `settlementRemaining`, serta mengirim snapshot menu.
- Detail delete memakai `DeleteAccess` selain pemeriksaan UI. Tombol tersembunyi tidak menggantikan izin server.
- Tier otomatis, harga manual yang dikunci, dan tombol kembali ke harga otomatis jangan dihilangkan.
- Gaji tetap memakai semua komponen, pembagi hari kerja, diterima manual terpisah, note, file, dan bon. Jangan “memperbaiki” formula bon tanpa keputusan bisnis.
- Privasi slip non-level-1 tetap personal. Administrasi login dan hak hapus tidak dilonggarkan sebagai efek samping pembukaan input.

## 6. Cara menjalankan ulang audit dengan aman

Dari root repository, dengan dependency frontend sudah tersedia:

```sh
npm --prefix Frontend run typecheck
npm --prefix Frontend test
node docs/audits/pos-2026-11-02/logic-audit.cjs
npm --prefix Frontend run dev -- --host 127.0.0.1 --port 5178
```

Terminal lain, gunakan Playwright yang tersedia di host. Contoh path runtime pada host audit:

```sh
NODE_PATH=/home/orion/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules \
  node docs/audits/pos-2026-11-02/browser-audit.cjs
```

Jika path itu tidak ada, cari runtime Playwright host atau gunakan instalasi terisolasi; jangan menambah dependency produksi hanya untuk menjalankan script audit. `AUDIT_BASE_URL` dapat diganti ke origin localhost lain. Script menolak origin nonlokal, memblokir service worker, mengintersep seluruh `/api/`, mengembalikan fixture untuk read/auth-refresh/permission, dan menolak mutasi bisnis. Aset selain origin dev diblokir.

Script browser adalah **perekam observasi baseline**, bukan regression suite yang sengaja mengharapkan semua bug sudah benar. Setelah perbaikan, ubah observasi menjadi assertion perilaku yang diinginkan. Kegagalan selector harus dibedakan dari bug aplikasi. Output ditulis ulang pada folder bukti.

Untuk backend setelah perubahan domain/CRUD:

```sh
php8.3 Backend/vendor/bin/phpunit -c Backend/phpunit.xml --do-not-cache-result
python3 Backend/tests/integration/pocketbase_transactions.py
```

Baca script integrasi sebelum menjalankan: saat baseline ia membaca **schema** dari SQLite dengan mode read-only, lalu membuat data/server sementara dan fixture. Pastikan binary/dependency tersedia serta port 18090/18080 bebas; jangan menghentikan layanan lain untuk mendapatkan port. Audit ini belum menjalankan dua perintah backend tersebut. Jangan mengganti target ke record bisnis nyata jika tes gagal menyiapkan lingkungan.

## 8. Build/deploy dan peringatan handoff

`datasource` tetap satu sumber koneksi. Gunakan `./compose`; jangan mengubah port/URL di banyak file. Hook/migrasi PocketBase terpasang langsung pada Docker operasional, sehingga edit untuk eksperimen dapat langsung memengaruhi layanan.

**Jangan menjalankan build default sebagai sekadar tes audit.** `Frontend/dist` terkait penyajian frontend, dan plugin `version-generator` di `Frontend/vite.config.ts` menulis hardcoded `dist/version.json`; `--outDir` saja belum menjamin build sepenuhnya terisolasi. Untuk verifikasi bundle, pakai salinan proyek/worktree terisolasi dengan output path yang benar; untuk deploy, ikuti prosedur proyek setelah perubahan disetujui.

Audit hanya menambahkan dokumentasi, script read-only, dan screenshot fixture. Tidak diperlukan restart atau migrasi untuk membaca hasilnya. Sesudah implementasi oleh agent berikutnya, build/deploy dan push harus dilaporkan sebagai tindakan terpisah, dengan hasil yang benar-benar telah dikonfirmasi.
